Three Approaches for UniIPCConnector Optimization

All three address OOM + adaptive routing + size gating, but differ in architecture

Approach A: MemoryPressureGuard (Recommended)

A pre-send guard checks GPU free memory before routing. If pressure is high, falls back to SHM/inline. Minimal changes to existing code.

Approach A: Guard-based Adaptive Routing
┌─────────────────────────────────────────────────────┐
│                  UniIPCConnector.put()                │
│                                                      │
│  ┌──────────┐    ┌──────────────┐    ┌────────────┐ │
│  │ GPU      │───▶│ MemoryGuard  │───▶│ Size Gate  │ │
│  │ Tensors  │    │ free_mem > X%│    │ nbytes > T │ │
│  │ in data  │    │ ?            │    │ ?           │ │
│  └──────────┘    └──────┬───────┘    └──┬────┬────┘ │
│                         │               │    │       │
│                     NO  │          YES  │    │ NO    │
│                         ▼               ▼    ▼       │
│                    ┌─────────┐   ┌────────┐ ┌──────┐ │
│                    │ Fallback│   │CUDA IPC│ │Inline│ │
│                    │ to SHM  │   │ send() │ │bytes │ │
│                    └─────────┘   └────────┘ └──────┘ │
│                                                      │
│  Memory Check: torch.cuda.mem_get_info(device)        │
│  Size Gate:    config.gpu_transport_min_bytes (64KB)  │
└─────────────────────────────────────────────────────┘

Pros

  • Minimal code changes — guard wraps existing send()
  • Directly addresses OOM via real-time GPU memory monitoring
  • No protocol changes — compatible with existing consumers
  • Fallback is transparent to caller

Cons

  • Point-in-time check — memory could fill between check and send
  • SHM fallback adds CPU round-trip latency under pressure
  • No consumer-side visibility into memory state

Approach B: Registry Budget + Flow Control

TensorRegistry gets a byte cap. Producer blocks or fails when full. Consumer sends capacity signals via control channel.

Approach B: Budget-based Flow Control
┌───────────────────┐         ┌───────────────────┐
│    PRODUCER        │         │    CONSUMER        │
│                    │  send() │                    │
│  ┌──────────────┐  │────────▶│  ┌──────────────┐  │
│  │ TensorRegistr│  │         │  │ recv() + ack │  │
│  │ max_bytes=2GB│  │         │  └──────────────┘  │
│  └──────┬───────┘  │         │        │           │
│         │           │         │   capacity_ack    │
│         │  FULL?    │◀────────│   ("ready", N)    │
│         │  block()  │         │                    │
│         ▼           │         │                    │
│  ┌──────────┐       │         │                    │
│  │ Semaphore│       │         │                    │
│  │ acquire()│       │         │                    │
│  └──────────┘       │         │                    │
└───────────────────┘         └───────────────────┘

Pros

  • Hard guarantee — never exceeds budget
  • Consumer-aware — flow control matches actual consumption rate
  • Predictable under any load pattern

Cons

  • Adds protocol complexity (new control messages)
  • Blocking send() could stall the producer pipeline
  • Choosing the right budget value is workload-dependent

Approach C: Three-Tier Unified Router

A unified routing decision that combines memory pressure, tensor size, and topology into a single decision point. Most comprehensive.

Approach C: Unified Adaptive Router
┌────────────────────────────────────────────────────────┐
│                   TransportRouter                       │
│                                                         │
│   Input: tensor(nbytes, device), gpu_mem_pressure       │
│                                                         │
│   ┌─────────────────────────────────────────────────┐  │
│   │  Decision Matrix:                                │  │
│   │                                                  │  │
│   │  nbytes < MIN_BYTES  ──────────────▶ INLINE      │  │
│   │                                                  │  │
│   │  gpu_mem_free < THRESHOLD ──────────▶ SHM        │  │
│   │                                                  │  │
│   │  nbytes >= MIN_BYTES &&                          │  │
│   │  gpu_mem_free >= THRESHOLD ─────────▶ CUDA_IPC   │  │
│   │                                                  │  │
│   │  (optional) !P2P_available ─────────▶ CUDA_COPY  │  │
│   └─────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘

Pros

  • Most complete — addresses all three problems in one design
  • Clean separation — routing logic isolated from transport implementations
  • Extensible — easy to add new transport strategies later

Cons

  • Most code to write and test
  • Three code paths to maintain per tensor
  • Decision matrix needs tuning for different GPU topologies
