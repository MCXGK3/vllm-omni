UniIPCConnector 传输策略配置

将不同的优化维度拆分为独立的配置选项，每个选项回答一个具体的动机问题

维度 1：GPU 张量的传输方式

控制 GPU 张量以什么方式跨进程传输

A1

CUDA IPC only（当前行为）

所有 GPU 张量走 CUDA IPC 零拷贝。动机：验证 CUDA IPC 在大数据量下是否真的导致 OOM，建立性能上界。

A2

SHM only

所有 GPU 张量先 .cpu() 再走 SharedMemoryConnector。动机：验证 SHM 是否在任何负载下都稳定，建立稳定性基线。

A3

CUDA Copy（急切拷贝）

IPC 打开后立即 copy_() 到本地 tensor，释放生产者端显存。动机：验证 "生产者尽快释放" 是否能缓解 OOM。

维度 2：大小阈值（与维度 1 组合使用）

小于阈值的 GPU 张量不走 GPU transport，直接转为 CPU bytes inline 传输

B1

无阈值（当前行为）

所有 GPU 张量统一走 GPU transport，无论大小。动机：作为基线，测量小张量走 IPC 的开销占比。

B2

gpu_transport_min_bytes 阈值

用户配置最小字节数（默认 65536）。小于阈值的张量 .cpu() → inline bytes。动机：验证小张量跳过 IPC 是否减少同步开销、提升稳定性。

维度 3：显存压力响应（与维度 1 组合使用）

当 GPU 空闲显存不足时，自动降级传输方式

C1

无压力检测（当前行为）

不监控显存，始终使用配置的传输方式。动机：基线，测量无干预下的 OOM 边界。

C2

显存压力降级

发送前检查 torch.cuda.mem_get_info(device)，空闲显存低于阈值时自动降级到 SHM。动机：验证 "通信数据积压" 假说 — OOM 是否由 TensorRegistry 积累导致。

推荐实验组合

每个维度的选项可以独立组合，逐步验证假设：

  1. 先测基线：A1+B1+C1（当前行为）→ 复现 OOM，记录 OOM 边界
  2. 测稳定性基线：A2+B1+C1 → 验证 SHM 是否永不 OOM
  3. 测大小阈值：A1+B2+C1 → 排除小张量干扰后，OOM 是否改善
  4. 测压力降级：A1+B1+C2 → 验证显存监控能否在 OOM 前介入
  5. 组合最优：A1+B2+C2 → 预期的最终配置
