UniIPCConnector 传输策略配置

将不同的优化维度拆分为独立的配置选项，每个选项回答一个具体的动机问题

维度 1：GPU 张量的传输方式

控制 GPU 张量以什么方式跨进程传输

A1

CUDA IPC only（当前行为·零拷贝）

所有 GPU 张量走 CUDA IPC，生产者持有张量直到消费者 ACK。动机：建立性能上界（零拷贝延迟最低），同时验证 生产者端 TensorRegistry 积累是否导致 OOM。

A2

SHM only

所有 GPU 张量先 .cpu() 再走 SharedMemoryConnector。动机：建立稳定性基线（GPU 显存无额外占用），验证 SHM 在任何负载下都不会 OOM。

A3

CUDA Copy（急切拷贝）

IPC 打开后立即 copy_() 到本地 tensor，生产者端尽快释放。动机：验证 消费者端 显存是否也会 OOM——当消费者积压多个请求时，copy 后的本地 tensor 同样会占用显存。

维度 2：大小阈值（与维度 1 组合使用）

小于阈值的 GPU 张量跳过 GPU transport，直接转为 CPU bytes inline 传输

B1

无阈值（当前行为）

所有 GPU 张量统一走 GPU transport，无论大小。动机：作为基线，测量小张量走 IPC 的同步+句柄提取+序列化开销占比。

B2

gpu_transport_min_bytes 阈值

用户配置最小字节数（默认 65536）。小于阈值的张量 .cpu() → inline bytes。动机：局部优化通信方式——小张量的 IPC 开销（stream sync + reduce_tensor + 序列化 IPC args）远超数据拷贝本身，走 inline 更合理。

维度 3：显存压力响应（与维度 1 组合使用）

当 GPU 空闲显存不足时，自动降级传输方式

C1

无压力检测（当前行为）

不监控显存，始终使用配置的传输方式。动机：基线，测量无干预下生产者/消费者各自的 OOM 边界。

C2

显存压力降级

发送前检查 torch.cuda.mem_get_info(device)，空闲显存低于阈值时自动降级到 SHM。动机：验证 "通信数据积压" 假说——OOM 是否由阶段排队导致 TensorRegistry/LocalCopy 积累，以及动态降级能否在 OOM 前介入。

实验矩阵

步骤 配置组合 验证目标
1 A1+B1+C1 当前行为基线：复现生产者端 OOM，记录 OOM 边界（并发数 × token 数）
2 A2+B1+C1 稳定性基线：验证 SHM 是否永不触发 GPU OOM
3 A3+B1+C1 消费者端 OOM：验证消费者积压时急切拷贝是否仍然 OOM
4 A1+B2+C1 大小阈值优化：测量小张量排除后的通信延迟改善
5 A1+B1+C2 压力降级：验证显存监控能否在 OOM 前成功降级
